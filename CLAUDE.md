# CLAUDE.md — job-hunter (Docker + VPS Senko)

## Что это
Пайплайн: парсит вакансии, скорит их и шлёт релевантные в Telegram.
Работает в Docker, деплоится на VPS Senko через git push → ssh pull → rebuild контейнера.

## Структура (важное)
- `config/settings.yaml`, `config/sources.yaml` — конфигурация парсинга и поиска.
- `config/profile/` — рантайм-профиль кандидата, который **читает бот**.
- `src/` — код; `src/matcher/pre_filter.py` — предфильтр (недавно доработан под CIS/русскоязычные вакансии).
- `docker-compose.yml`, `Dockerfile`, `requirements.txt`, `.env` — окружение.
- `PROFILE.md` — человекочитаемый мастер-профиль (источник правды о кандидате).
- `docs/` — справочники: `career_consultant_prompt.md`, `TARGET_CRITERIA.md`, `target_criteria_REFERENCE.py`, `AUDIT.md`, `project_audit_prompt.md`.

## Правила работы
- **PROFILE.md — мастер.** `config/profile/` держи в соответствии с ним; второй источник правды не создавай.
- Актуальные решения владельца — в разделе 2 PROFILE.md и runtime-профиле.
  Не путать семь технических ролей предфильтра с приоритетами поиска.
  Личные зарплатные ожидания и текущую стратегию не копировать в публичные
  инструкции: это создаёт второй источник правды и публикует личные данные.
- Рабочий пайплайн (Docker, парсеры, `pre_filter.py`) **не ломать**; уже сделанную CIS/русскоязычную доработку **не дублировать**.
- Крупные изменения — на отдельной ветке, через **Plan mode**, с диффом. На VPS файлы репозитория руками не править.
- Критерии целевых вакансий живут в `config/criteria.yaml`, логика — в `src/matcher/pre_filter.py`. Ролей **семь**: **Crypto/Web3 Operations**, **Web3 Support**, **AI Automation** (индустриально-независимая), **Web3 QA** (ручное тестирование), **AML/комплаенс**, **Поддержка в финтехе/IT**, **Удалённые продажи** на входящих. `target_criteria_REFERENCE.py` — только эталон, как модуль НЕ подключать.
- **Репозиторий ПУБЛИЧНЫЙ (портфолио).** Поэтому личные данные в него не коммитятся: `.env`, `PROFILE.md`, `config/profile/*` (кроме `*.example`), `docs/resume/` — всё в `.gitignore`. Профиль доставляется на VPS через `scp` (как `.env`) и подключается bind-mount'ом. ⚠️ После `git reset --hard` на VPS папка `config/profile` пересоздаётся → нужен `docker compose up -d --force-recreate`, иначе bind-mount остаётся на удалённом inode и бот не видит профиль.

## Проверки и деплой

- Локальные проверки — через установленный Python без Docker:
  `C:/Users/sanny/AppData/Local/Python/pythoncore-3.14-64/python.exe -m pytest -p no:cacheprovider`
  и тот же Python с `-m ruff check src/ tests/ tools/`. Голые `python`, `py`,
  `python3` могут быть неработающими Windows-шими; `.venv` в проекте нет.
- Если локальные проверки недоступны — использовать проверенный запасной способ:
  архив проверяемой версии → `scp` в отдельный каталог `/tmp` на VPS → тесты
  в отдельном временном контейнере. Рецепт — `docs/PROJECT_REVIEW.md`, раздел
  «Правила на всю сессию». Не запускать тяжёлые проверки одновременно с прогоном бота.
- Docker Desktop, локальную Docker-сборку и локальный запуск бота для обычной
  проверки и деплоя не запускать. `docker compose up` запускает реальный
  `run_once()` и может отправлять карточки из устаревшей локальной БД и конфликтовать
  с Telegram polling на сервере.
- Выкатка после разрешения пользователя: локальные коммит и push →
  `ssh vps-senko` → `/opt/job-hunter` → `git pull --ff-only` →
  `docker compose up -d --build`. Перед push применять `push-guard.sh` из
  `C:/Users/sanny/.claude/skills/vps-deploy/tools/` по инструкции скилла.
  Если пользователь уже явно поручил выкатку, повторное разрешение не требуется.
- Перед пересборкой проверить диск (`df -h /`) и по логам убедиться, что текущий
  прогон завершён. Расписание сверять с актуальным конфигом; время логов бота — UTC.
  При нехватке места действовать по `vps-deploy`, не удалять данные бота.
- После выкатки проверить версию кода в контейнере и логи стартового прогона.
  Статуса `Up` недостаточно. Для изменений Python нужен `--build`, одного
  `restart` недостаточно.
